# 高校掌上校园 App 协议笔记

对一个高校掌上校园类 App 的**协议结构与自动化工程**做的整理。

只写**思路**：怎么定位、怎么验证、结论是什么、工程上要注意什么。
不包含任何真实账号、学号、姓名、学校、token、密钥，也不含可直接运行的利用代码。

## 三篇

| # | 文档 | 内容 |
|---|---|---|
| 1 | [登录链路](docs/01-login.md) | 学校路由、版本门判别、会话行为探测、多账号会话池 |
| 2 | [课表结构](docs/02-timetable.md) | 天桶语义、"排课计划串"为什么不可信、周次换算、分支判别 |
| 3 | [签到机制](docs/03-checkin.md) | 三种方式的验证边界、受理与落库的区别、三层判定、引擎设计 |

## 阅读顺序

三块是**单向依赖**的：

```
登录 ──身份四元组──→ 课表 ──教学班/课程/节次──→ 签到
```

登录拿不到身份，课表无从谈起；课表给不出教学班，签到没有入参。
所以按 1 → 2 → 3 读。每篇末尾都有一节「未验证的部分」，那些是真实存在的盲区。

## 方法总纲

贯穿三篇的同一套方法：

1. **先抓包，再反编译** —— 抓包告诉你"发了什么"，反编译告诉你"为什么这么发"。只有抓包会漏掉条件分支，只有反编译会漏掉运行时实际取值。
2. **用对照实验代替猜测** —— 改一个参数、跑两次、比对响应差异。本文所有结论都来自这种单变量对照，不是从代码"看起来像"推出来的。
3. **区分「官方客户端这么做」和「服务端要求这么做」** —— 很多字段客户端会填，服务端却根本不读。把两者混为一谈会导致大量无效工作。
4. **受理 ≠ 成功** —— 服务端返回的"成功"往往只是"请求格式对了"。真实状态要另找接口回查。

## 环境说明

文档描述的是一套集中式 JSP 控制器架构：所有业务动作打同一个入口，
用 `action` / `step` 两个参数路由，外层再套一层自定义信封。

这类架构在国内高校信息化产品里很常见，本文的**方法**对同类系统普遍适用，
但具体参数名、常量、分支条件都属于某一版本客户端的实现细节，会随版本变化。
