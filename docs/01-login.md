# 一、登录链路

## 1. 这类系统长什么样

不是"一个 App 对一个服务器"，而是三层：

```
App
 │
 ├─① 学校目录服务（全局一个）
 │     输入：学校代码或校名关键字
 │     输出：该学校专属的 serviceUrl + 认证方式 + 模式位
 │
 ├─② 学校网关（每校不同，也可能全部指向同一个总网关）
 │     所有业务请求打这里，用 action / step 路由
 │
 └─③ 子系统（教务、IM、在线教学…）
       登录后从响应的子系统清单里拿到各自 url 与凭据
```

**关键设计含义**：登录不是"填账号密码然后 POST"，而是"先解析学校，再决定打到哪"。
跳过第①步直接猜网关，在跨校场景下必错。

## 2. 怎么定位登录入口

三个来源交叉验证，缺一个就会走偏：

| 来源 | 能拿到 | 拿不到 |
|---|---|---|
| 抓包（代理 + 证书） | 实际发出的字段、真实取值、响应结构 | 条件分支、字段来源 |
| 反编译（jadx / Hopper） | 所有分支、字段怎么算出来的、常量 | 运行时实际取值 |
| 主动探测（构造请求） | 服务端到底读哪些字段、校验什么 | 正常流程长什么样 |

### 一个具体的坑

反编译能看到「A 条件下走分支 X，否则走分支 Y」，但**看不出你所在的环境属于哪个条件**。
我在这上面浪费过时间：代码里有一条"学校开通教务直连就用简化参数"的分支，
从响应字段看自己的学校**明明属于直连**，但实际只有走另一条路才有数据。

教训：**分支判定必须用实测响应验证，不能只看判断条件**。
判别信号很简单——拿不到数据时返回的是**空 body（非 JSON）**，而不是错误码。
空 body 就是"你走错分支了"。

## 3. 密码处理：编码不等于加密

第一件要做的事是确认"到底有没有真加密"。判别方法：

1. 在反编译里找到密码进请求体之前调用的函数
2. 看它的实现，而不是看它的名字

常见真相：所谓加密只是一个**编码函数**（URL 百分号编码、Base64、十六进制）。
这类函数可逆、无密钥、无随机数。

三个快速判别信号：

| 信号 | 含义 |
|---|---|
| 同一密码两次请求的密文**完全相同** | 没有随机数/IV → 不是正经加密 |
| 函数里没有密钥、没有 IV、没有填充模式 | 只是编码 |
| 密文长度与明文长度**成固定比例** | 编码（如每字节 3 字符），不是分组加密 |

我这边的结论：密码只是编码了一层，链路上没有真正的加密层。
**这意味着一件事——安全性完全依赖传输层**。这一点值得在任何类似系统上先确认，因为它决定了你要不要花时间去找"密钥"。

## 4. 版本门：下限校验还是精确匹配

几乎所有这类客户端都带一个版本校验。**必须先判别它的语义**，否则会陷入"改端口号试到天荒地老"。

判别实验（低成本，用假凭据即可，只观察到"进入账号校验"这一步）：

```
用版本号 V 登录 → 记录错误文案
换 V-1 → 文案变化？
换 V+1 → 文案变化？
换 V+50 → 文案变化？
```

三种可能的语义：

| 语义 | 现象 | 应对 |
|---|---|---|
| 精确匹配 | 只有 V 通过，V-1 和 V+1 都被拒 | 必须拿到服务端认可的那个值 |
| 下限校验（>=） | V 及以上全部通过，低于 V 全部被拒 | 传给一个明显更高的值即可 |
| 完全不校验 | 任何值都能进到账号校验 | 不用管 |

我这边的结论是**下限校验**，而且门槛**可能已经高于官方包内置的版本号**——
也就是说官方原版客户端自己都过不了这个门。这个现象值得记录：
它说明"版本门"是运营侧独立配置的，不跟随客户端发布节奏。

再补一层：客户端里通常还有**第二条版本通道**（独立的版本查询接口），
返回的字段里有一个 `versioncode`。这个值**很容易被误当成登录门槛**，
但它往往是"学校侧配置的版本"，与客户端版本无关，且可能比客户端内置值还旧。
两条通道要分开看，别混。

### 自愈做法（工程上）

```
登录失败
  ↓ 文案命中「必须更新 / 请升级 / 版本过低」类关键词？
  ↓ 是
用假凭据按阶梯逐档探测（升序），第一档"进入账号校验"的就是门槛
  ↓
写回配置，重建客户端重试一次
```

要点：
- **探测必须用假凭据**，不能拿真账号去撞门槛
- 阶梯要覆盖足够大的跨度（小时级步进 + 末段兜底 +1），否则未来抬门会失效
- 探测结果要持久化，不能每次启动都重新探

## 5. 会话行为的四个探测

登录成功后，token 怎么用、能不能共用、什么时候失效——这四个实验能一次问清：

| 实验 | 做法 | 观察 |
|---|---|---|
| 有有效期吗 | 存下 token，隔很久再用 | 是否返回"口令失败"类错误 |
| 是否单点 | 同一账号登录两次，比较两个 token | 两个是否相同；旧的是否失效 |
| 会话载体 | 看响应头 | 是否有 session cookie（注意 HttpOnly/Secure） |
| 身份是否被校验 | 故意传错身份字段 | 是否有"非本人"拦截 |

我这边的实测结果值得单独记一笔：**不是单点**。同一账号两次登录拿到不同 token，旧的仍然可用。
这意味着"脚本登录会把手机踢下线"的担心是多余的。

另一个反直觉的观察：**故意传错身份字段时，服务端返回 HTTP 200 + 空 body**，
而不是 403 或错误码。没有"非本人"拦截分支。
排查时不要把空 body 当成"网络问题"，它是服务端的正常应答。

## 6. 过期自动续期

必须做，否则脚本会**静默空转**：token 过期后每个请求都返回业务错误，
如果错误处理写得粗，看起来就像"老师一直没发起签到"。

做法：在请求层统一拦截，检测到"口令失败"类业务错误 → 重新登录 → **重放本次请求一次**。

要注意与网络重试分层：

| 层 | 重试什么 | 不能重试什么 |
|---|---|---|
| 网络层 | 超时、连接错误 | HTTP 4xx/5xx、业务错误码 |
| 会话层 | token 过期（重登后重放一次） | 其它业务错误 |

两条规则不能混：把业务错误也重试会导致"重复提交"类事故。

## 7. 多账号：一套会话池

如果要跑多个账号（自己的 + 家人的 + 同学的），架构上有个关键取舍。

### 取舍：每账号一个实例，还是共用配置

如果 `Settings` 是个全局单例，多账号会互相踩。两种解法：

| 方案 | 代价 |
|---|---|
| 把账号字段一路透传到每个函数 | 改动面巨大，容易漏 |
| **账号对象提供一个 `to_settings(base)`，用不可变替换生成新配置** | 上层零改动 |

第二种明显更划算：底层协议代码一行不用改，只是喂给它不同的配置对象。

### 会话池的三个要点

1. **每账号一把锁**：同一账号的并发请求串行化，避免重复登录
2. **懒登录**：第一次用到才登，不是启动时全登一遍（多账号时启动会打爆上游）
3. **取用前重读账号表**：改密码后必须立即生效，而不是等进程重启

第 3 点很容易漏。如果账号对象在构造时被缓存，改了密码之后旧凭据会一直被用来重登，
表现是"改完密码这个账号永远登录失败，重启才好"。

### 账号存哪

从配置文件挪进数据库（一张 `accounts` 表 + `UNIQUE(学校, 学号)` 约束）。
好处：增删改、开关、单账号独立的重试参数都能落到行上；坏处：**密码是明文**。

明文这件事要诚实对待：它和放在配置文件里是同等风险等级。
真正的改进不是"找地方藏密码"，而是**把数据文件排除出版本控制**。

## 8. 失败归因表

排查时最有用的东西。按文案反查原因，比读代码快：

| 现象 / 文案 | 原因 |
|---|---|
| 「必须更新后才能登录」类 | 版本门 |
| 「账号不存在」 | 已过版本门，账号错（能拿到这个文案说明版本是对的） |
| 「口令失败」 | 密码错，或 token 过期（先试自动重登） |
| HTTP 200 + 空 body | 身份字段传错，或走错了接口分支 |
| 空 body 且非 JSON | 走错分支（见 §2 的坑） |
| "是否当前学期"标记在配置里恒为空 | 不能靠它判断当前学期，要回落取第一项 |

最后一条值得强调：**"当前学期"这个字段不是所有学校都会填**。
依赖它做默认选择，在某些学校上会直接拿到空值。

## 9. 未验证的部分

诚实记录盲区：

- 密码编码是否在所有学校上都是同一种形态（只验证了一所）
- token 的**确切**有效期（只知道"几个小时到一天之间"这个量级，未精确测定）
- 服务端是否在别处（如管理后台、风控侧）记录了登录 IP —— 客户端侧和登录响应里都没有，但不等于服务端不存
- 版本门抬升的触发条件（是运营手工改，还是跟某个发布流程绑定）

## 10. 工程清单

按依赖顺序，做一套能跑的登录链路需要：

1. 学校解析（代码/名称 → 网关）
2. 密码编码（按实测判断，不要按函数名判断）
3. 请求信封（如果目标版本用了外层包装）
4. 版本门自愈
5. token 过期自动重登 + 请求重放
6. 失败归因（文案 → 原因，写成表）
7. 多账号会话池（锁 + 懒登录 + 改密生效）
8. 凭据落库 + 数据文件排除出版本控制
