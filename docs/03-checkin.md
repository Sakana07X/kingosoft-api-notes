# 三、签到机制

## 1. 三种方式，判定位置不同

签到方式在不同学校/不同课程下会变，常见三种：

| 方式 | 学生要做什么 | 验证发生在哪 |
|---|---|---|
| 一键定位 | 点一下（或什么都不做） | **客户端** |
| 手势/图案 | 画出老师设定的图案 | **客户端** |
| 二维码 | 扫老师屏幕上的码 | **服务端** |

**这张表是整篇最重要的东西**。"验证在客户端"意味着：

- 服务端收到的只是"一个结果数字"，它无法独立复算
- 客户端拿到判定所需的全部输入（基准坐标、图案原文）都是**服务端自己下发的**

所以前两种方式的自动化难度，和"直接把表单填对并提交"是同一个量级；
第三种不行，因为码值必须服务端比对，而码值不在学生侧接口里。

> 这不是"能不能绕过"的问题，而是**协议设计把信任放在了客户端**。
> 这类设计在很多行业系统里都能看到，值得作为一类模式来识别：
> 凡是"判定输入由服务端下发、判定过程在客户端完成、结果回传"的设计，
> 服务端侧就只有形式校验。

## 2. 「一键定位」和「手势」共用一个提交动作

反编译里能确认一件事：画完图案（本地比对通过）之后，走的是**和一键定位同一个提交函数**。

也就是说手势签到的完整流程是：

```
教师发起（图案明文下发）
   ↓
学生画图案 → 本地字符串比对
   ↓
比对通过 → 触发定位 → 算距离
   ↓
提交：坐标 + 距离 + 图案原文 + 方式标记
```

**图案对完还要定位、还要距离。** 这一点在二手资料里经常被写掉，
照那个实现会缺两个必填字段。

## 3. 一个必踩的参数坑：节次必须传区间

签到状态查询里有个"节次"参数。直觉上传"第 3 节"（数字 3）是合理的。
**实际会一直返回「老师还未发起签到」。**

对照实验（同一天、同一门课、同一时刻，只改这一个参数）：

| 传值 | 响应 |
|---|---|
| `3` | 未发起 |
| `"3"`（字符串） | 未发起 |
| `4` | 未发起 |
| **`"3-4"`** | **已结束 + 真实时间戳 + 真实考勤码** |

服务端是按**节次区间**匹配签到任务的。传单节数字，它会认为"没有这一节"。

这个坑的杀伤力在于：**它的表现是"老师没发起"，而不是报错**。
如果系统里有一层"状态不是进行中就跳过"的逻辑，就会**永久静默跳过**——
每天都不签到，日志里一条错都没有。

### 教训

> 当"功能不工作"但"没有任何错误"时，优先怀疑**参数形态**（数字 vs 字符串、
> 单值 vs 区间），而不是怀疑业务逻辑。形态错通常表现为"空结果"，
> 逻辑错才表现为"报错"。

正确做法：课表里的节次字段本身就是区间串，**原样透传**，不要做任何"取第一个数字"的转换。

## 4. 距离：客户端算，服务端只收数字

提交报文里有两个字段：学生坐标（`lng,lat`）和**距离米数**。

距离是**客户端算好之后作为数字上送**的。服务端收到的是：

```
{
  坐标: "lng,lat",     ← 学生自己报的
  距离: "6"            ← 学生自己算的
}
```

反编译里能确认算法细节（有意思的是它用的不是标准 haversine，
而是把经纬度转成三维单位向量后取弦长再反三角，结果等价但写法不同）：

```
u  = (cos φ cos λ, cos φ sin λ, sin φ)
d  = asin( |u₁ − u₂| / 2 ) × (地球半径 × 2)
```

三个格式细节容易踩：

| 细节 | 正确形态 | 错误形态 |
|---|---|---|
| 距离类型 | **截断整数**（6.58m → `"6"`） | 保留小数 `"6.58"` |
| 零距离 | 发**空串** | 发 `"0"` |
| 坐标 (0,0) | 发**空串** | 发 `"0,0"` |

### 边界：老师可能根本没给基准点

教师端发起签到时如果定位失败（或重试次数耗尽），**会带着空基准点照样发起**。
此时学生端的行为是：**不算距离、坐标和距离都发空串、照样提交**。

如果你的实现里写了"没有基准点就放弃"，每次这种情况都会静默漏签。
这是一个纯收益的修复：多一个分支，少一次事故。

## 5. 受理 ≠ 成功（本篇第二个核心洞察）

提交后服务端返回一个 `flag`（或类似的成功标记）。**不要相信它。**

`flag == "1"` 的真实含义是"**请求被受理了**"，不是"记录已落库"。
官方客户端自己也只看这个标记就弹"签到成功"。

实际观察到的错位：

| 情况 | `flag` | 真实结果 |
|---|---|---|
| 正常 | `1` | 落库 |
| 返回体写着"签到成功"但标记不是 1 | ≠`1` | 可能落库了 |
| 重复提交 | ≠`1`，文案"你已签到" | **已落库**（这是好消息，不是失败） |
| 提交成功但后续被教师端覆盖 | `1` | 缺勤 |

第三种尤其要注意：**"你已签到，无需重复签到"是成功证据，不是失败原因。**
把它当失败处理，会发出错误的告警邮件。

### 三层判定模型

```
① 标记层     resp_ok: flag == 1  或者  文案命中成功关键词
                     ↓ 都不能单独作为结论
② 回查层     再查一次考勤结果接口，按「日期 + 节次区间」命中记录
                     ↓
③ 落库层     考勤码 == 正常 才算真的签上
```

第②层要注意**落库有延迟**（观察到最长几十秒量级）。
所以回查要带重试间隔，且"查不到"应当记为**未核实**而不是失败——
未核实的正确处理是"换更近的位置再提交一次"，不是发告警。

## 6. 两个接口，两个语义

特别容易混淆的一对：

| 接口 | 回答的问题 | 什么时候有值 |
|---|---|---|
| 状态查询 | 老师**现在**发起签到了吗？ | 只有进行中时才有可提交所需字段 |
| 考勤结果 | 我**历史上**每节课是什么状态？ | 一直有，含未发起的课（无记录） |

用途完全不同：

- 状态查询 → 决定"现在能不能提交"
- 考勤结果 → 决定"我到底签上没有"

状态值的实测语义（注意有负值）：

| 状态 | 含义 | 能提交吗 |
|---|---|---|
| `1` | 已发起，进行中 | ✅ 唯一可提交 |
| `-1` | 未发起 | ❌ |
| `-4` | **已结束** | ❌，但 body 里带时间戳和考勤码，可用于复盘 |

`-4` 那个设计很有用：签到结束后接口仍然返回结束时间、时长、本人考勤状态，
所以**事后能判断"我漏了没有"**。

### 用一个不可靠的字段当"进行中"标志会出事

有些响应里有个 `qdzt` 之类的小整数，看起来像"签到进行中"标志。
实测同一场签到里它**会变**（一次读到 `2`，几分钟后读 `1`），不是稳定状态位。

判"能不能提交"只能用**状态查询返回的那个状态码**，别用这个。

考勤码的映射是固定的七种（正常/缺勤/迟到/事假/早退/病假/公假），
`00` 表示正常。展示时优先用响应里的文字字段，码值用于逻辑判断。

## 7. 自动化引擎：一轮 tick 该怎么做

### 朴素实现的三个坑

```
❌ 遍历今日课程 → 逐门提交
```

问题：

1. **没发起也提交** → 无意义的请求，且可能被服务端记账
2. **已经签过还提交** → 收到"你已签到"（虽然无害，但日志噪音）
3. **老师没发起的课占满了重试次数** → 真正发起时已经没额度

### 改进后的顺序

```
① 取今日课表（缓存）
② 并发查每门课的状态（4 路）
③ 先分流：已签 / 未发起 / 已结束 / 进行中
④ 只对「进行中」的进入提交流程
⑤ 提交前随机延迟（打散时刻，避免全班同一秒）
⑥ 延迟后**重查**状态：已结束就放弃（不提交）
⑦ 提交 → 三层判定 → 未核实则换更近的位置重试
⑧ 已结束但本人未签 → 记「漏签」事件 + 告警
```

第⑤⑥两步值得说：**随机延迟 + 延迟后重查**。
签到窗口往往只有几分钟到十几分钟，如果全班用同一个工具，
提交时刻整齐划一是最明显的异常特征。延迟 25~90 秒既能打散，又不至于错过窗口。

而延迟之后必须**重查状态**——窗口可能在这几十秒里关闭了，此时提交是无效请求。

### 距离阶梯

如果第一次提交没核实到，不要用同一个位置重试。用**逐级贴近**的阶梯：

```
第 1 次：距基准点 3~10m
第 2 次：2~6m
第 3 次：1~4m
第 4 次：0.5~2.5m
```

理由：服务端如果做距离校验，阈值未知；越贴近越安全，
但也不能贴 0m（会和别人撞、也可能撞"必须在范围内"的下界）。

> 需要诚实说明：**服务端到底有没有复核距离，未验证**。
> 反编译里没有任何距离常量，看起来阈值在服务端侧；
> 但"没看到"不等于"不存在"。所以阶梯是防御性设计，不是已知必要。

### 去重与幂等（多账号下最易错）

签到事件的天然键是 `日期 + 教学班 + 节次`。**这个键不含账号**。

如果多个账号共用一份 `已处理` 集合，**同班的第二个人会被当成"已签"直接跳过**。
所以：

- 每个账号一个独立的引擎实例（各自的已完成集、待处理集、缓存）
- 日志和事件里带账号维度
- 从业者角度看，这不是"多账号功能"，而是"单账号功能 × N 份状态"

第二个去重坑：**进程重启后会重放"失败"的事件**。
如果恢复逻辑把"失败/未核实/未发起"的记录重新放回待处理队列，
而没排除"这一节已经有成功记录"的，那么每重启一次就会补记一条成功事件
（表现为"同一次签到被核验了三次"）。

修法很简单：恢复时先算出"已有成功记录的键集合"，跳过它们。

## 8. 误报失败的四条成因

这一节是从多次错误告警里反推出来的，价值可能超过前面的机制说明。

| # | 成因 | 表现 | 修法 |
|---|---|---|---|
| 1 | 只看 `flag` | 已成功但标记不是 1 → 判失败 | 加文案成功判定 + 回查 |
| 2 | 「你已签到」被当成失败 | 重复提交时收到 | 文案含"已签/无需重复" → 按成功处理 |
| 3 | 落库延迟 | 提交后立刻回查查不到 | 回查带重试；查不到记"未核实"，不告警 |
| 4 | 失败与成功各发一封 | 用户收到自相矛盾的两封信 | 只在最终状态确定后发；成功时撤回未发的失败 |

第 4 条容易被忽视：如果"提交失败"和"迟到核验成功"分别发一封邮件，
用户会同时收到"签到失败"和"签到成功"，然后不知道该信哪个。

原则：**告警只在最终状态确定后发一次**，中间态不发。

## 9. 服务端能/不能看到什么

值得单独整理，因为它决定了"自动化会不会被发现"这个问题的真实答案。

| 信息 | 服务端能看到吗 | 依据 |
|---|---|---|
| 学生坐标 | ✅ | 客户端上送 |
| 距离米数 | ✅ | 客户端算好后上送 |
| 提交时刻 | ✅ | 服务端记录 |
| 签到 IP | ❌ 业务接口不返回 | 教师端可见字段里没有 IP |
| 设备指纹 | 弱 | 客户端侧那个"设备标识"方法直接返回空串 |
| 请求来源特征 | 部分 | UA、请求头顺序等 |

看到"设备标识恒定为空串"这一点时我的判断是：
**这套系统在设计上就没打算做设备维度风控**，所以在这上面做文章没有收益。
真正能被察觉的是行为层面的异常（时刻整齐、坐标高度集中），
这也是第 7 节要加随机延迟的原因。

## 10. 未验证的部分

- 服务端是否真的复核距离（反编译无常量 → 疑似在服务端，但未证实）
- 重复提交是否幂等（不幂等则可用于探测"是否已签"，有用但未测）
- 签到窗口的上下限（只观察到 5~15 分钟量级，未测边界）
- 迟到判定的触发条件（是提交时刻 vs 开始时刻的差值？未验证）
- 教师端"代签"是否走同一套校验（参数形态相同，但服务端可能区别对待）

## 11. 工程清单

按依赖顺序：

1. 状态查询（**节次传区间串**）
2. 分流器（已签 / 未发起 / 已结束 / 进行中）
3. 三种提交（共用函数只差两个字段；二维码单独一条）
4. 距离计算 + 三个格式细节 + "无基准点"分支
5. 三层判定（标记 / 回查 / 落库码）
6. 距离阶梯重试
7. 随机延迟 + 延迟后重查
8. 考勤结果聚合（出勤率 = 落库码统计）
9. 每账号独立状态（引擎实例、去重键、日志维度）
10. 告警只在最终状态发一次
11. 漏签检测（已结束 + 本人未签 → 事件）
