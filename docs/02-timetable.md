# 二、课表结构

## 1. 一次请求只拿一周，响应是「天桶」

课表接口不是"给我整学期"，而是"给我第 N 周"，响应结构是：

```
{
  顶层:  学期起始日 / 最大周次 / 当前请求的周次
  week1: [ ...周一的课... ]
  week2: [ ...周二的课... ]
  ...
  week7: [ ...周日的课... ]
}
```

**这里有一个必须钉死的命名陷阱**：

`week1` … `week7` 不是"第 1 周到第 7 周"，而是"周一到周日"。
`week3` = 周三，`week7` = 周日。

我从反编译确认了这一点：日期转桶序号的函数是 `get(DAY_OF_WEEK) - 1`，再把 `0` 映射成 `7`。
即 `周一 → 1`，`周日 → 7`。原生代码取"今天是星期几"对应的**那一个桶**，
从头到尾不跨桶合并。

### 为什么这个陷阱致命

如果误以为是周次，你会写出"遍历 week1..week7 拼成 7 周课表"的代码。
结果是把周一到周日的课塞进同一周，去重后看起来"课很多"，
但每一门的节次/日期全是错的。

## 2. 确认天桶语义的方法

不要靠命名猜，用对照实验：

1. 固定周次，请求两次，确认稳定
2. 拿一门**已知上课日**的课（比如你确定周三下午有课）
3. 看它出现在哪个桶里

如果出现在 `week3`，命名含义就确定了。这个实验 5 分钟能做完，
比读一堆代码可靠。

## 3. 周次从哪来

响应顶层有一项是**第 1 周周一的日期**（下称"学期起始日"）。周次直接算：

```
week = (今天 - 学期起始日).days // 7 + 1    下限 1
```

所以拉课表的最小开销是**两次请求**：一次拿 `week=1`（顺带拿到起始日），一次拿目标周。
如果当前恰好是第 1 周，两次能合并成一次。

**优化点**：早期实现是"1 到最大周次逐周拉 + 合并去重"，16 周就是 16 次请求，
而且合并之后还得靠别的字段过滤。改成"先探测周次，只拉一周"后是 2 次请求。

## 4. 「排课计划串」不可信

课表里通常有个字段写着这门课的周次计划，形如：

```
3-15周
2-11,13-15周
单周 / 双周
(3-11周)
```

看着天然适合用来过滤"这门课本周上不上"。**但它不能用来过滤。**

### 对照实验

固定一门课，比较相邻两周的响应：

| 请求 | 顶层起始日 | 该课出现在哪个桶 |
|---|---|---|
| 第 N 周 | 第 N 周周一 | 「周三」桶里**有**这门课 |
| 第 N+1 周 | 第 N+1 周周一 | 「周三」桶里**没有**这门课 |

而计划串在两次响应里**完全相同**（都写 `3-15周`，第 N+1 周明明在区间内）。

结论：**服务端按实际排课下发**（含调课、临时停课、教师请假），
计划串只是排课计划，与实际执行情况已经脱钩。

### 正确做法

**只拉目标周那一周，只取今天对应的那一个桶，不做任何计划串过滤。**

代价是多一次请求（探测周次），换来的是不会混入不该出现的课、也不会漏掉临时加的课。
这个交换非常划算。

顺带一提：计划串本身还是有用的——用来**展示**（"这门课上到第 15 周"），
但不能用来**判定**。

## 5. 两条互斥分支：空 body 是判据

课表接口常有两条互斥路径，取决于学校是否开通了教务直连：

| 分支 | 参数形态 | 常见结果 |
|---|---|---|
| 教务直连 | 学号（去前缀） | **空 body，非 JSON** |
| 平台代理 | 完整用户标识 + 一个 channel 参数 | ✅ 真实数据 |

**判别方法**：拿不到数据时，看返回的是"错误码"还是"空体"。

- 返回错误码 → 参数值错
- 返回**空 body 且 Content-Type 不是 JSON** → **走错分支了**

这一点很容易误判成"学校没配课表"或"接口失效"。
另外注意：在代理分支里多传几个看起来"合理"的字段（uuid、学校代码等）
会直接导致业务错误码，所以**不要"顺手把知道的字段都带上"**。
参数集要最小化，只带实测必需的。

## 6. 数据归一化

原始对象字段多、命名不统一、还有嵌套。建议归一化成扁平结构，同时**保留一份 raw**：

| 归一字段 | 来源 | 用途 |
|---|---|---|
| 课程名 / 课程代码 | 直接字段 | 展示、提交 |
| **教学班代码** | 直接字段 | **签到的必需入参**（见第三篇） |
| 节次代码（如 `03,04`） | 直接字段 | — |
| **节次区间串（如 `3-4`）** | 直接字段 | **签到的必需入参，必须保留原样** |
| 教师代码 / 姓名 | 直接字段 | 展示 |
| 天桶序号 1~7 | 桶序号 | 判定"今天" |
| 教室 / 周次 | 直接字段 | 展示 |
| `raw` | 原始对象全量 | 排障、溯源 |

保留 `raw` 的成本很低，收益很高：所有"这个字段哪来的"的问题都能当场回答，
不用重新抓包。

## 7. 班级信息：读出来，不要猜

判断"我在哪个班"，不要从课表的名称字符串里切，也不要让用户手填。

正确的做法是找一个**返回同班名单**的接口：

```
输入：教学班代码 + 学期 + 学年 + 学期序号
输出：每条含 学号 / 姓名 / 班号 / 班级名 / 专业 / 学院 / 年级 / 培养层次 / 性别
```

然后在名单里按**自己的学号**匹配，命中那条就是自己的班级信息。

三个要点：

1. **这是"接口算出来的"事实**，不是猜的，也不是让用户填的
2. 学期参数常是拼接形态（学年 + 学期序号），要能拆
3. 一门课可能有**多个教学班**（课表里同一门课出现两次），要遍历 `教学班代码` 去重后再查

> 这一条在工程上特别值得做。曾经因为"直接从课程名推班级"得到错误结论，
> 后来改成读名单接口，才发现真实班级与猜测不符。**能读就不要推。**

## 8. 学期列表的两个坑

1. "是否当前学期"标记**不是所有学校都会填** —— 实测有学校恒为空串。
   依赖它选默认学期，会在那些学校上拿到空值。回落策略：取第一项。
2. 学期代码是机器码（形如 `学年 + 学期序号`），不是人读格式。
   展示要用名称字段，但发请求要用代码字段，别混。

## 9. 工程上的缓存与并发

| 场景 | 策略 |
|---|---|
| 今日课表 | 缓存 300 秒，**key 里必须带日期**（跨天自动失效） |
| 学期全量课表（第 7 节那种统计用） | 缓存 1800 秒，**key 里必须带账号 id** |
| 逐周拉全学期 | 4~6 路并发，不要再放大 |

两个"必须"都是踩过的：

- 缓存 key 不带日期 → 跨天还在用昨天的课表，签到直接打空
- 缓存 key 不带账号 → **A 账号的课表给 B 账号看**（多账号场景下必现）

并发上限也值得记：把连接池调大（8→16）后实测**反而变慢**（8.1s → 13.3s）。
学校网关对突发并发不友好，4~6 路是甜点。压测会短暂打爆限流额度，几分钟自恢复。

## 10. 未验证的部分

- 不同学校的桶结构是否完全一致（只在一所验证过；有的系统可能用 `mon`/`tue` 之类命名，或 8 个桶含"周末"合并）
- 调课/补课在响应里是否有显式标记（只观察到"课消失了"，没观察到替代形态）
- 最大周次字段是否总等于真实周数（存在课程 15 周结束但该字段更大的情况）
- 学期全量课表逐周拉时，周末/假期周返回空桶·还是返回上一周数据

## 11. 工程清单

1. 学期列表（注意"是否当前学期"标记可能为空）
2. 周次探测（用学期起始日算，不要靠猜）
3. 单周拉取（分支判别靠"空 body"，参数最小化）
4. 天桶展开（记住：`weekN` 是星期 N）
5. 今日抽取（只取一个桶，**不做计划串过滤**）
6. 归一化（扁平字段 + 保留 raw）
7. 班级反查（读名单接口，不猜）
8. 缓存（key 带日期 + 账号 id）
9. 并发 4~6 路
